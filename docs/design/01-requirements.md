## 1. MVP の要件とモジュールの対応

企画書 §15 の MVP 13 項目を、§12.3 のモジュールに割り当てる。

| # | MVP の項目 | 主なモジュール | オフライン |
|---|---|---|---|
| 1 | Windows デスクトップアプリ | Electron（main・preload） | — |
| 2 | 3 スロットのキーワード抽選 | Keyword Dictionary・Random Generator（`src/core`） | ○ |
| 3 | スロットごとのカテゴリ選択 | Random Generator・UI | ○ |
| 4 | 複数カテゴリ選択 | Random Generator・UI | ○ |
| 5 | スロット固定・個別再抽選 | Random Generator・UI | ○ |
| 6 | A/B モード | UI（モードは画面の状態。データは共通） | ○ |
| 7 | A モードの自由入力 | UI・Idea Storage（下書き） | ○ |
| 8 | B モードの AI 複数案生成 | Idea Generator | × |
| 9 | Sign in with ChatGPT | Authentication | × |
| 10 | アイデア保存 | Idea Storage | ○ |
| 11 | お気に入り登録 | Idea Storage | ○ |
| 12 | 保存済みアイデア一覧 | Idea Storage・UI | ○ |
| 13 | コピー・Markdown 出力 | Idea Exporter（`src/core`）・main（ファイル保存） | ○ |

依存の向き: 2〜7・10〜13 は AI なしで完結する。8 は 9（または別の接続手段）に依存する。企画書 §19 の順（抽選と A モード → AI → 保存・出力）はこの依存と合っている。

## 2. 未確定事項と初期値の案

企画書に書かれていない、または読み方が 2 通りある点。

### 抽選

| ID | 未確定のこと | 初期値の案 | 理由 |
|---|---|---|---|
| D-1 | スロットでカテゴリを 1 つも選んでいないとき | 「全カテゴリ」とみなす | 抽選できない状態を作らない |
| D-2 | 単語が 0 語のカテゴリ | 抽選の対象から外す（カテゴリの均等抽選にも入れない） | 空振りを防ぐ |
| D-3 | 「同一キーワードの重複を原則回避」（§5.6）の範囲 | 必須: 1 つの組み合わせの中でキーワード 1 と 2 を同じにしない。努力目標: 同じスロットで直近 20 回に出た語をなるべく避ける | 回すたびに新しい語が出ることが「もう一回回したい」に効く |
| D-4 | 手動入力した語の扱い | 入力したスロットを自動で固定する。辞書には足さない | 一括再抽選で消えないようにする |
| D-5 | ジャンル一覧の「その他」（§5.4） | 抽選の対象にしない（分類の名前であってジャンルではない） | 「その他」が出ても発想の起点にならない |
| D-6 | ジャンルの階層（§5.4・U-3） | 内部では親カテゴリ（例: アクション系・思考系・経営/育成系・物語系・その他）を持ち、選ぶ画面では親カテゴリ単位の複数選択だけを出す | 初期 UI を複雑にしない |
| D-7 | 乱数 | `src/core` は乱数の関数を引数で受け取る。テストでは固定の列を渡す | テストできるようにする |
| D-8 | 「現在の組み合わせをコピー」の形 | `自動販売機 × 寄生 × 経営シミュレーション` の 1 行 | そのまま外部 AI に貼れる |

### A モード・B モード

| ID | 未確定のこと | 初期値の案 | 理由 |
|---|---|---|---|
| D-9 | A モードの入力途中の内容をどこまで保持するか | モードの切り替え・画面の移動に加えて、アプリの再起動後も残す（下書きとして自動保存） | 思いつきを失わない |
| D-10 | 再抽選したときの A モードの下書き | 消さない。下書きには「書き始めたときの組み合わせ」を記録し、組み合わせが変わったら小さく知らせる | 再抽選を気軽にできるようにする |
| D-11 | A モードで保存するアイデアの形 | 本文（自由記述）は必須、タイトルは任意（空なら本文の 1 行目） | 自由記述を妨げない |
| D-12 | A モードの下書きを AI に渡すか | 渡さない | 企画書 §6.1「AI に引っ張られない」の逆向きの配慮。人の案を AI の材料にしない |
| D-13 | 生成数を変えたときの方向の配分（§7.2） | 王道 → 変化球 → 実験的 の順に繰り返す（例: 5 案 = 王道 2・変化球 2・実験的 1） | 単純で予測できる |
| D-14 | N 案を 1 回の依頼で出すか、N 回に分けるか | 1 回の依頼で N 案を出させる（同じ文脈で互いに違う案にさせる）。届いた案から順にカードを出す | 企画書 §7.4「アイデア同士の差別化」 |
| D-15 | AI の出力の言語 | 日本語 | 辞書・画面が日本語 |
| D-16 | 生成中に再抽選したとき | 生成は続ける。結果には生成を始めたときの組み合わせを表示する | §11.4「生成中も他の操作を妨げない」 |

### 保存・履歴・出力

| ID | 未確定のこと | 初期値の案 | 理由 |
|---|---|---|---|
| D-17 | 一時的な生成履歴（§9.3）を残す量 | 保存していない生成案は、直近 200 件まで残して古いものから消す | 「保存」と「履歴」を分ける |
| D-18 | 「キーワードによる検索」（§9.1）の範囲 | タイトル・キーワード・ジャンル・本文・メモの部分一致 | 何で探しても見つかる |

| D-20 | AI の案の本文の保存形 | 項目ごとの構造（JSON）で保存し、表示と出力のときに組み立てる | 出力の形を後から変えられる |

## 3. 実装上のリスク

| ID | リスク | 影響 | 対策 |
|---|---|---|---|
| R-1 | Sign in with ChatGPT のプラン利用はプレビュー。仕様や対象が変わりうる。OSS アプリに承認が要るかが公式文書で読み切れない（[調査](../research/sign-in-with-chatgpt.md)）→ 試作では承認なしで動いた（2026-11-05） | B モードが使えない・作り直し | AI の接続を差し替えられる形にする（企画書 §13.5）。設計の前に実際にサインインして 1 回生成する試作で確かめる（Q-6） |
| R-2 | プラン利用の対象は Plus・Pro の利用者（公式の案内）。無料プランでは B モードを使えない | 使える人が限られる | A モードを完全に単独で使えるようにする。別の接続手段を検討（Q-4） |
| R-3 | プラン利用の経路では `temperature`・`max_output_tokens` などを指定できない | 多様さ・長さを引数で調整できない | 指示文（方向・禁止事項・字数の目安）で調整する。評価用の組み合わせで出力を見比べる（R-5） |
| R-4 | 構造化出力（JSON Schema）がこの経路で使えるか公式文書に書かれていない。関数ツールは使える → 試作で JSON Schema も使えた（2026-11-05） | 案を項目に分けて受け取れない | 関数ツールで受け取る案を第一に、だめなら区切りのある文章を解析する。STEP 6 の最初に確かめる |
| R-5 | AI の案が無難・ありがちになる（企画書 §18-5）。製品の価値の中心 | 「もう一回回したい」にならない | 方向ごとの指示、ありがちな型の禁止、キーワードをルールへ反映させる指示。固定の組み合わせ 10 通り程度で出力を比べる評価の手順を作り、結果を LEARNINGS に残す |
| R-6 | 辞書の質が体験を決める。偏り・似た語の連続・意味の取りにくい語 | 抽選が楽しくない | カテゴリごとの語数の目安（U-2）、重複の検査（済）、抽選結果の見本を人が眺める点検 |
| R-7 | `node:sqlite` の安定度（Node 24 では正式版ではない） | 将来の Electron で API が変わる | 保存はインターフェースの後ろに置き、必要なら `better-sqlite3` に替えられるようにする（U-1） |
| R-8 | トークンの保管 | 漏れると他人がプランを使える | トークンは main プロセスだけが持ち、renderer に渡さない。Windows の DPAPI（Electron の `safeStorage`）で暗号化して保存する。ログに出さない |
| R-9 | サインインの受け口（127.0.0.1 の一時的な HTTP サーバー） | ほかのプロセスからの不正なコールバック | `127.0.0.1` だけで待ち受け、`state`・`nonce`・PKCE を検査し、1 回受けたら閉じる。時間切れを設ける |
| R-10 | Web 版への移植（企画書 §12.1） | 公式文書のこの流れはローカルで動くアプリ向け。Web 版は別の契約（Web サイト向けの連携、提携企業の待機リスト）になる | Web 版の AI 接続は別途検討と明記する。`src/core` と画面は使い回せる形を保つ |
| R-11 | 署名のないインストーラーは Windows の SmartScreen で警告される | 配布したときの印象 | STEP 8 で決める（U-5） |
| R-12 | スコープの膨張（企画書 §18） | 完成が遅れる | AGENTS.md §3。MVP の外のものは STATE の未決事項に提案として書くだけにする |

## 4. メンテナーの判断が要ること

| ID | 判断すること | 推奨 |
|---|---|---|
| Q-4 | AI の接続手段に、Sign in with ChatGPT のほかに「自分の OpenAI API キー」を入れるか。API キーの利用料はユーザー本人の OpenAI アカウントに課金される | 入れる。ただし設定で明示的に選んだときだけ使い、課金されることを画面に書く。Sign in with ChatGPT が使えないときに自動で切り替えない（企画書 §13.5） |
| Q-5 | 派生生成（企画書 §8）を MVP に入れるか。§15 の MVP の一覧には無いが、§11.2 の結果カードには「派生生成」がある | 最小の形（固定の 4 操作 + 自由指示、元の案は上書きしない）を MVP に入れる。生成の仕組みは B モードと共通なので追加の手間が小さい |
| Q-6 | Sign in with ChatGPT の試作（実際にサインインして 1 回生成する）を STEP 3 の前に行うか。メンテナーがブラウザで自分の ChatGPT アカウントにサインインする必要がある | 行う。設計の前に、承認の要否・使えるモデル・構造化出力の可否（R-1・R-4）を確かめる |
